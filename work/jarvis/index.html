01

Problem

I ran Claude Code and Codex sessions side by side across my projects and life, and nothing held what each agent was doing, what was blocked or what was done. The agents had the mirror problem: each needed to know what was theirs, what others held and what had changed, without loading the whole history.

I owned the product: the brief, the rules, the decisions and every release. Jarvis was built with Claude Code and Codex on my brief; they designed the mechanisms and wrote the code, contracts and tests.

02

The system

Jarvis makes no model calls. Its users are AI agents, so the product question is what an agent may do to a shared record, and through which door. The parts marked carry rules I set.

03

Approach

  • Evidence before design. The plan started from how I actually work: 704 Claude prompts and 62 Codex threads showed where my sessions begin. Most start inside a project, so the folder can name the project; the rest start at a root and have to be classified from the conversation.
  • A spike before the build. Twenty rounds of four writers and one reader on one record, with no claim lost, and the session hooks proven on both harnesses.
  • First, a workspace the agents could load. On the heaviest project the instruction file was 204 KB, and a first request cost 109.4k tokens of input before any work began. I dictated the brief: one instruction file both harnesses read. Startup input fell to 27.0k tokens and the file to 6 KB, and nothing was hard-deleted on the way.
  • Then the record. I asked for Jarvis, approved the merged Claude Code and Codex plan as its foundation, and named it. The agents’ core came first, the interface after.
  • Adversarial review as the release gate. Codex reviewed each phase at its highest effort, and a HOLD sent the work back to the builder; most phases took two to five rounds. A phase was released when I closed its task on the board.
  • Feedback from use. After each phase I used the board and dictated what was wrong. That is how planning moved from the week to the day, and how one approval came to cover a night out and a late wake-up.
  • Gates removed after measuring. Three weeks of agent traffic showed that the friction came from checklists and proof steps, not from authority. Readiness became something Jarvis computes, my approval became a grant I can take back, and the doors that matter stayed where they were.
  • Each part on the model that fits. One chat on the strongest model had done three large tasks alone, because the rule to split work was text an agent could skip. Now a plan names its parts, Jarvis turns them into subtasks and sets each helper agent’s model, and the card shows what really ran.
04

Key decision

The call
Only a human door acts as me: agents cannot close, drop or lock work, and the board acts as me only after Touch ID.
Alternatives
  1. A flag in the record that agents are told to respect.
  2. A macOS confirmation dialog for every action I take.
Why
On my Mac an agent with a shell can call any command, so a rule it is asked to follow is not a boundary. The record needed a door only a person can open. The first one was a macOS dialog, and a dialog for every drag was tiring; in my words, “touch id work better”. With Touch ID on the board, closing work stays mine without slowing me down.
05

What I built

The rules of authority and planning below are decisions of mine with a date, tied to my words or to a plan I approved. Where an agent made a call inside my plan, the record credits the agent.

Authority

rules I set

What an agent may do to a shared record, and how I can prove who approved what.

  • Only I close

    When
    A task is to be closed, dropped, reopened, deleted or locked
    If
    The request comes through the board, after a fresh Touch ID tap
    Then
    It happens, as me
    Else
    The command line and the MCP server refuse

  • A go-ahead becomes a grant

    When
    An agent passes on my approval of a piece of work
    If
    My words are found in a message I typed, or I accepted its plan, or I tapped Approve on the board
    Then
    A grant for that work: agents may start it, add subtasks, schedule it and hand it off, each use recorded as theirs
    Else
    It is refused

  • I can take it back

    When
    I type wait, stop, hold, cancel or not yet about that work, or tap Revoke
    Then
    The grant ends and never revives

  • Ready is computed, not filled in

    When
    A task is read
    If
    It has a done-when
    And
    No question for me is open
    Then
    It is ready, and Jarvis fills in or flags the rest

    An audit of the agents' use showed the friction was in checklists, not in authority. The checklists went; the doors stayed.

  • Review says how to check it

    When
    An agent finishes
    If
    An outcome with a line that says how to check it
    And
    A second agent's PASS, when I asked for one
    Then
    The task moves to Review, for me

Routing

rules I set

Which model does which part of a bigger job, so a small part does not quietly run on the most expensive model.

  • A plan states its parts

    When
    An agent submits a plan of two or more parts
    If
    A table names, for each part, who does it, the model and the effort
    Then
    I see the plan
    Else
    It goes back to the agent once, before I see it

  • Subtasks come from the plan

    When
    I accept the plan
    Then
    Jarvis creates one subtask per part, with its model and effort

  • The record sets the model

    When
    The chat starts a helper agent for a subtask
    Then
    It runs on that subtask's model and effort, even if the chat asked for another

  • Planned next to ran

    Then
    Each card shows what really ran beside the plan, and warns when the chat did the work itself

Correctness

Mechanisms the agents designed inside my plan. Most came out of Codex's HOLD findings.

  • One holder, no lost updates

    When
    An agent writes to a task
    If
    It holds the task's one claim
    And
    The version it read is still current
    Then
    The write lands, in one transaction
    Else
    HELD or CONFLICT

  • Edited outside? Stop

    When
    A task was changed outside Jarvis
    Then
    Every write is refused as TAMPERED until I accept the task

  • The ranking explains itself

    importance 0 to 40 · deadline 15 to 60scheduled 5 to 20 · priority goal 15unblocks others: 6 each, cap 18doing 8 · next 5 · inbox −5, by where it stands

    One score, and every card on Today shows its first two reasons.

Planning the day

rules I set

  • Attention decides the lane

    auto: an agent can run it unattendedquick: small, light, humanfocus: needs my full attention

  • Estimates are computed

    Then
    An estimate is the similarity-weighted median of the time past tasks took

    I never pick one.

  • How tight may a day get?

    at 90% or more: automaticbetween 60 and 90%: ask meunder 60%: only on my word

    I set these thresholds.

  • A late start in one act

    When
    I slept in
    Then
    Sleep is recorded, open blocks move forward, fixed ones stay, and the day is planned in the same write

    The agents' tasks have been running since midnight. Mine wait for me.

It is made of very little: Node 24 with its built-in SQLite, a hand-written MCP server and its own WebAuthn check, with no runtime dependencies.

06

Outcome

Jarvis is the tool I run my own work and my agents’ work on every day, built for one Mac. I plan the day, approve and close on the board; the agents work from its brief. Bigger work is planned in parts, and each card shows which model really did it. It also exports a dated history of past work to my career evidence folder, the record I was missing for clients, a CV and this portfolio.

07

Learnings

  • Separate the live copy from the build copy on day one. The hooks, MCP server and command line ran the repository’s working tree, so a schema change migrated the live database mid-build. Builds moved to separate worktrees; a pinned release copy is my next call.
  • A rule an agent can skip will be skipped. The rule to split bigger work across models lived in a text the agents read, and one chat did three large tasks alone on the strongest model. It became a check at the moment a plan is submitted.
  • Approval has to be provable where it happens. The board once showed work as proposed by Codex after I had approved it in the session. Approval now lives in the conversation, and the board follows it.
